# Authentication Architecture

SelfVault implements a flexible authentication system following the **BYOI (Bring Your Own Infrastructure)** philosophy. This means you can choose your preferred authentication provider without being locked into a specific vendor.

## Authentication Providers

### 1. Supabase Auth (Default)

Supabase Auth is the default provider in V1. It provides:

- Email/password authentication
- Social login (Google, GitHub, etc.)
- Email verification
- Password reset
- JWT token management

**Configuration:**

```env
AUTH_PROVIDER=supabase
SUPABASE_URL=https://your-project.supabase.co
SUPABASE_ANON_KEY=your-anon-key
SUPABASE_SERVICE_KEY=your-service-key
```

### 2. Local Auth (Self-Hosted)

Local Auth is a fully self-managed authentication system. It provides:

- Email/password authentication
- JWT tokens generated by the backend
- Password hashing with bcrypt
- No external dependencies

**Configuration:***

```env
AUTH_PROVIDER=local
JWT_SECRET=your-super-secret-jwt-key-minimum-32-characters
```

**Note:** When using Local Auth, users are stored in your database with hashed passwords. No external service is required.

## Choosing a Provider

| Feature | Supabase | Local |
|---------|----------|-------|
| External dependency | Yes (Supabase) | No |
| Social login | Yes | No (can be added) |
| Email verification | Yes | No (can be added) |
| Password reset | Yes | No (can be added) |
| Scalability | High | Depends on your setup |
| Cost | Free tier available | Free (self-hosted) |
| Setup complexity | Easy | Very Easy |

## Configuration Examples

### Full Supabase Stack

```env
AUTH_PROVIDER=supabase
STORAGE_PROVIDER=supabase
DATABASE_URL=postgresql://...supabase...
SUPABASE_URL=https://abc.supabase.co
SUPABASE_ANON_KEY=...
SUPABASE_SERVICE_KEY=...
```

### Full Self-Hosted Stack (MySQL + MinIO + Local Auth)

```env
AUTH_PROVIDER=local
STORAGE_PROVIDER=s3
DATABASE_URL=mysql://user:pass@localhost:3306/selfvault
JWT_SECRET=your-secret-key
S3_ENDPOINT=http://localhost:9000
S3_ACCESS_KEY_ID=minioadmin
S3_SECRET_ACCESS_KEY=minioadmin
S3_BUCKET=selfvault
```

### Hybrid (Supabase Auth + S3 Storage)

```env
AUTH_PROVIDER=supabase
STORAGE_PROVIDER=s3
DATABASE_URL=postgresql://...
SUPABASE_URL=https://abc.supabase.co
SUPABASE_ANON_KEY=...
SUPABASE_SERVICE_KEY=...
S3_ENDPOINT=https://s3.amazonaws.com
S3_ACCESS_KEY_ID=...
S3_SECRET_ACCESS_KEY=...
S3_BUCKET=my-bucket
```

## API Endpoints

### Authentication Routes

| Method | Endpoint | Description |
| -------- | ---------- | ------------- |
| POST | `/api/auth/login` | Login with email/password |
| POST | `/api/auth/register` | Register a new user |
| POST | `/api/auth/logout` | Logout (invalidate session) |
| POST | `/api/auth/refresh` | Refresh access token |
| GET | `/api/auth/provider` | Get current auth provider config |

## Frontend Integration

The frontend automatically detects which auth provider is configured:

```typescript
import { authService } from './services/auth';

// Login
const result = await authService.login(email, password);
console.log(result.tokens.accessToken);

// Register
const result = await authService.register(email, password, username);

// Check authentication
if (authService.isAuthenticated()) {
  // User is logged in
}

// Logout
await authService.logout();
```

### Manual Provider Selection

You can force a specific provider in the frontend:

```env
# Frontend .env
VITE_AUTH_PROVIDER=local
```

Or in code:

```typescript
import { setAuthProvider } from './services/auth';

setAuthProvider('local');
```

## Security Considerations

### JWT Secret

When using Local Auth, ensure your `JWT_SECRET` is:

- At least 32 characters long
- Randomly generated
- Never committed to version control

Generate a secure secret:

```bash
openssl rand -base64 64
```

### Password Requirements

- Minimum 8 characters
- Passwords are hashed with bcrypt (cost factor 12)
- Never stored in plain text

### Token Expiration

- Access tokens: 1 hour
- Refresh tokens: 7 days

## Extending the System

### Adding a New Auth Provider

1. Create a new provider class implementing `IAuthProvider`:

```typescript
// backend/src/auth/KeycloakAuthProvider.ts
export class KeycloakAuthProvider implements IAuthProvider {
  async verifyToken(token: string): Promise<AuthUser | null> {
    // Implement Keycloak token verification
  }
  // ... other methods
}
```

2. Register it in the factory:

```typescript
// backend/src/auth/index.ts
case 'keycloak':
  return new KeycloakAuthProvider();
```

3. Add frontend service:

```typescript
// frontend/src/services/auth/KeycloakAuthService.ts
export class KeycloakAuthService implements IAuthService {
  // Implement methods
}
```

## Migration Guide

### From Supabase to Local Auth

1. Update your `.env`:

```env
AUTH_PROVIDER=local
JWT_SECRET=your-new-secret
```

2. Run migrations:

```bash
npx prisma migrate deploy
```

3. Create new user accounts (existing Supabase users won't have passwords in your DB)

### From Local to Supabase Auth

1. Create a Supabase project

2. Update your `.env`:

```env
AUTH_PROVIDER=supabase
SUPABASE_URL=...
SUPABASE_ANON_KEY=...
SUPABASE_SERVICE_KEY=...
```

3. Users will need to re-register through Supabase

## Summary

> **"Supabase is a default provider, not a requirement."**

SelfVault's authentication is designed to be:

- **Flexible**: Choose your provider based on your needs
- **Portable**: Switch providers without changing application logic
- **Secure**: Industry-standard practices (JWT, bcrypt)
- **Self-hosted friendly**: Run without any external dependencies
